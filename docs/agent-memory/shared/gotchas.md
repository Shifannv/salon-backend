# Gotchas

- Shell is Git Bash on Windows. Run backend commands from `backend/`. A `cd` persists between calls, so prefer absolute paths.
- Cached `.pyc` files show Python 3.14 locally; CI and the Docker image use 3.12.
- `SET LOCAL request.jwt.claims` must run on the same session as the work (`get_authenticated_session` in `backend/app/api/deps.py`), or audit triggers stamp no actor.
- Cache hits on salon detail, services, staff and QR must revalidate publication in Postgres. A cache entry is never authorization.
- `backend/migrations/versions/` holds Alembic `.py` revisions only. Their SQL sidecars (and the 001 baseline) live in `backend/migrations/sql/`; reports and evidence live in `backend/migrations/reviews/` (excluded from the Docker image). Revision files resolve sidecars via `parents[1] / "sql"`.
- The Mumbai investigation runners live in `backend/scripts/migrations/` (see its README; not app code, never run the DB-touching ones without approval). `supabase-schema-backup/` at the repo root is local-only and untracked. Evidence JSON keeps historical pre-restructure paths on purpose; details in `backend/docs/migrations/CLEANUP_PLAN.md`.
- Plain `pytest` can fail at collection with `No module named 'psycopg2'` when the local `.env` has a non-asyncpg `DATABASE_URL`. `psycopg2` is not a dependency; run with `ENVIRONMENT=local DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/salon_platform` as process env (never read `.env`).
- Never `git stash -u` here: `core.autocrlf` rewrites untracked LF files to CRLF on pop and breaks the SHA-256 evidence seals. Compare against `git archive HEAD` extracted to a scratch dir instead.
- Migrations 0038–0040 are prepared-only Mumbai migrations with production-specific review guards (Supabase-managed privileges, `current_setting('mumbai_review.server_effective_before')`). They fail on any fresh postgres. Integration tests use `_TEST_HEAD = "0037_customer_processing_charge"` as the upgrade target, not `"head"`. Do not change this until the Mumbai gates all pass.
- `Settings.database_url` now normalises `postgresql://` → `postgresql+asyncpg://` via a field_validator. If you see `ModuleNotFoundError: No module named 'psycopg2'` at startup, the DATABASE_URL env var is using the plain scheme; the validator fixes it automatically.
- Windows worktree has `core.autocrlf=true`: `tests/unit/test_fake_provider.py` (2 fixture tests) and `test_migration_tool_paths.py::test_offline_bundle_matches_sealed_files` (privilege-matrix.csv) fail locally from CRLF files and are expected to pass on Linux CI. Do not "fix" sealed evidence.
- On this Windows profile pytest's default temp dir is not writable; run tests that use `tmp_path` with `--basetemp=<scratch dir>`, and use `backend/.venv/Scripts/python.exe` (system Python has no pytest).
- `.github/workflows/backend.yml` triggers on every push and PR (tests + image build) but deploys only from `main` via manual dispatch with approval, and only with `migration_target=0040_fastapi_only_access` (held Mumbai migration). No workflow runs `alembic stamp` or deploys Cloud Run.
- The media cleanup worker scans all three managed R2 prefixes with no test filter: never point it at a shared bucket.
- Public salon responses (list, nearby, detail, services, staff) must never carry `qr_token`; only `GET /v1/walkin/{qr_token}` may echo the caller's own. `WALKIN_BASE_URL` must end in the web route (`/s`) because the printed QR is `<base>/<token>`. Payment capability (`payment_options`) is computed per response, never cached.
- Real-Postgres integration tests: start a throwaway `postgres:18` container on a spare port (for example 55432), set `MIGRATION_TEST_DB=postgresql://postgres:<throwaway>@127.0.0.1:55432/postgres` as process env, run, then `docker rm -f` it. Port 5432 on this machine is a native Postgres that is not disposable; never point the suite at it.
- Production config is Cloud Run + Secret Manager `salon-production-env`, not `backend/.env`. Editing local `.env` (Resend key etc.) changes nothing in production; a deployed setting needs a reviewed Secret Manager update. Mail to support@/info@ lands in Zoho (MX), so Resend MCP cannot verify receiving.
- `salon-production-env` holds blank placeholder lines (for example `ACCOUNT_DELETION_SECRET=`): treat a blank value as unset, replace the line in a new version rather than appending a duplicate key. Secret Manager readback can change line endings or trailing newlines, so verify a new version by parsed key/value pairs, not byte-exact comparison.
- Cloud Run auto-deploy (`cloud_run_auto.py`) uses `approved_schema_release()` to gate deploys with migration differences. It is hardcoded to admit only a specific delta (currently 0053-0055) from a specific baseline commit SHA. Any deploy where the production image baseline does not match that SHA — or carries additional migrations — is refused. Future migration batches require a new receipt file at `backend/deployments/schema-*.json` and a matching entry in `approved_schema_release`. Do not attempt to bypass this gate; create the receipt through the documented review process.
- GitHub rulesets and classic branch-protection are independent. Disabling a classic rule in Settings → Branches → edit does NOT disable a Ruleset with the same target. Both `main` and `shifan` rulesets in this repo target `refs/heads/main`; both must be disabled to allow a direct push bypass. Re-enable them after the emergency push.
